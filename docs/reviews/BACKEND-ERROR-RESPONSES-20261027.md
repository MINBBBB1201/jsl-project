# 공개 오류 응답과 미등록 경로 수정 · 2026-10-27

미등록 경로를 기존 500 대신 명시적인 404로 처리하고 요청 URL·쿼리를 응답에 반사하지 않도록 수정했다. 공통 오류 응답은 `NODE_ENV`와 관계없이 기존 production의 공개 계약을 사용한다. 개발용 오류 객체·스택은 HTTP 응답에서 제거했다. [이슈 #41](https://github.com/MINBBBB1201/jsl-project/issues/41)의 코드 수정이며 운영 적용은 아직 하지 않았다.

## 변경 범위

- `backend/src/middleware/error.middleware.js`: `notFoundHandler`를 추가했다. 운영 오류는 정수 400-599 상태와 문자열 메시지만 공개한다. 예상 밖 오류는 기존 일반 500 JSON으로 응답하고 서버 로그로 전달한다.
- 오류 정규화가 실패하거나 로그 저장이 예외를 던져도 일반 500 JSON을 유지한다. `{ ...err }` 복사 대신 원본 속성을 읽어 비열거 오류 이름도 판별한다. 이미 헤더를 보냈으면 `next(err)`로 위임하며 새 응답을 쓰지 않는다.
- `backend/src/server.js`와 `backend/tests/helpers/app.js`: 같은 `notFoundHandler`를 모든 등록 라우트 뒤, 공통 오류 처리 앞에 연결했다. DB 검사·CORS·인증·컨트롤러 순서는 바꾸지 않았다.
- `backend/tests/error-response.test.js`: 실제 Express와 공통 미들웨어를 loopback HTTP fixture에서 검사한다. 기존 앱·DB를 시작하는 `server.js`를 테스트 목적으로 import하지 않는다.

| 구분 | 수정 후 공개 응답 |
| --- | --- |
| 라우트 처리까지 도달한 미등록 경로 | 404, `{status: "fail", message: "Route not found."}` |
| 기존 운영 오류 | 기존 production의 상태와 `status`·`message` 유지 |
| 인식한 DB 입력 오류 | 기존 공개 400 계약 유지. 개발 모드에도 같은 계약 적용 |
| 예상 밖 오류·정규화 실패·잘못된 운영 오류 상태 | 500, `{status: "error", message: "Something went wrong!"}` |
| 이미 헤더 전송 | 응답 재작성 없이 Express에 위임 |

공개 응답과 서버 로그는 구분한다. 예상 밖 원본 오류의 서버 로그 기록은 유지한다. 컨트롤러가 직접 반환하는 JSON 오류와 기존 입력 오류 메시지의 내용은 이번 수정 범위가 아니다.

## 검증

기준 main은 `c8c5489a662ae9aab354335483332116f1962072`다. 처음 선별한 5개 검사에서는 3개 통과·2개 실패를 확인했다. 실패 항목은 development의 예상 밖 오류 응답과 헤더 전송 후 재응답이었다. 이 결과를 수정 후 전체 검사와 같은 검사 묶음으로 표현하지 않는다.

수정 후 백엔드 Jest 전체 **6개 묶음·144개 검사**가 통과했다. 새 오류 응답 검사 50개가 포함된다. development·production·test·미설정 환경, 일반/운영 오류, DB 입력 오류·비열거 오류 이름, 잘못된 오류 상태, 정규화·로그 실패, 성공 응답, 미등록 GET·POST·HEAD, 헤더 전송 후 위임을 확인했다.

백엔드 전체 ESLint, 변경 JS 4개 Prettier·Node 구문, diff 검사를 통과했다. 테스트는 기존 의존성과 MongoDB 7.0.24 바이너리를 재사용했고 다운로드·설치를 하지 않았다. 검사 시작 시 여유 메모리 기준을 확인하고 heavy lock 하나를 사용한 뒤 해제했다. 폐기 가능한 로컬 DB만 사용했으며 새 작업 폴더에 생긴 빈 로그 두 파일만 정리했다.

[검증 요약과 소스 해시](evidence/backend-errors-20261027/validation.json)에 실행 범위·도구 버전·기준 커밋을 기록했다. 전체 Jest 원시 출력·캐시·DB·실행 환경 설정은 커밋하지 않는다. JS 변경이므로 타입 검사는 대상이 아니며 프런트 build·화면 캡처는 실행하지 않았다.

### 실제 서버의 로컬 기동 보완

같은 코드 head `a5ff7ecc`의 실제 `src/server.js`를 별도 프로세스로 기동했다. 무작위 임시 인증값을 사용하는 폐기 가능한 로컬 MongoDB에 연결하고 스케줄러를 비활성화했다. 임시 preload는 listen 주소를 `127.0.0.1`로 제한하고 준비 알림을 전달하며 로그 transport를 비활성화한다. 라우트·DB 검사·오류 처리기는 대체하지 않았다. 인증값은 기록하지 않았다.

개발 모드에서 8조건이 통과했다: health 200·연결 상태, 루트 200, 일반 미등록 GET 404, 미등록 고지 GET 404, HEAD 404·빈 본문, 비로그인 알림 403, 잘못된 JSON의 일반 500, CORS 사전요청 204. 검수 요청은 loopback으로만 보냈고 실제 문의를 제출하지 않았다. 이 8조건은 위 Jest 144개와 별도 실행이다. 잘못된 JSON의 일반 500은 기존 production 계약이며 이를 400으로 바꾸지는 않았다.

종료 시 기존 SIGTERM 처리기를 호출했고 제한 시간 내 프로세스 종료를 관찰했다. 자식 프로세스의 숫자 종료 코드는 기록하지 않았다. 임시 MongoDB와 잠금은 정리했다. 이 검사는 실제 Render 배포 검수가 아니다.

## 한계와 운영 적용 전 조건

- 기존 의존성 설치를 재사용했다. 기록한 핵심 버전의 lockfile 일치는 확인했지만 새 `npm ci` 환경 재현은 아니다.
- 새 50개 HTTP fixture와 실제 서버 기동 보완은 구분한다. 후자는 실제 초기 DB 연결과 위 8개 응답만 확인했으며 DB 재연결 장애·전체 라우트 통합 검사는 아니다. 헤더 전송 후 위임은 미들웨어 수준 검사이며 실제 스트림 연결 종료는 미검증이다.
- 공통 DB 재연결 미들웨어가 먼저 실패하면 미등록 경로 처리에 도달하기 전 기존 DB 오류가 반환될 수 있다. 순서를 이동하지 않았다. 모든 공개 API의 오류 정보 노출을 전수 해결했다고 주장하지 않는다.
- 공개 Render의 운영 모드·배포 설정·로그는 이번 회차에서 조회하거나 변경하지 않았다. 병합·배포 후 없는 경로·일반 오류·기존 API 응답을 실제 서버에서 별도로 확인해야 한다. production 모드와 서버 로그 접근·보유 설정도 운영 담당자가 확인해야 한다.
- PR #25의 새 문의 고지 API, 정책 승인·보유/삭제·업체/국가, DB 인덱스·배포 계약은 별도 조건이다. 이 수정으로 문의 접수 준비나 출시 완료를 선언하지 않는다.

프런트·디자인·슬라이드·애니메이션·정책 값·문의 계약·계정·환경·의존성·lockfile은 보존했다. 기존 checkout에 다른 작업의 변경이 있고 기존 브랜치들이 미병합·사용 중이어서 정리하지 않았다. 이번 작업은 최신 main에서 분리한 `codex/backend-error-responses` 브랜치에서 진행했다.
