# 공통 API 오류 문구 읽기 · 2026-10-28

일부 프런트 호출부는 기존 `error`와 `errors[0].msg`만 읽어 공통 오류의 `message`를 표시하지 못했다. [이슈 #43](https://github.com/MINBBBB1201/jsl-project/issues/43)에서 인증 요청·대시보드 조회·공개 화물 조회에 같은 읽기 규칙을 연결했다. 디자인·성공 응답·인증 코드·문의 계약은 보존했다.

## 변경

- 새 `getApiErrorMessage`는 유효한 문자열 `error`, 첫 검증 오류의 문자열 `msg`를 먼저 읽는다. 둘 다 없으면 `status`가 `fail` 또는 `error`인 공개 오류의 문자열 `message`를 읽는다.
- 객체·배열·비문자열·빈 문자열·공백뿐인 문구와 분류되지 않은 `message`는 기존 HTTP 대체 문구로 처리한다. 오류 객체·스택을 직렬화하거나 다른 필드를 탐색하지 않는다.
- 유효한 기존 문자열의 공백까지 그대로 반환한다. 대시보드도 같은 규칙을 쓰므로 첫 `errors[0].msg`를 추가로 읽을 수 있다. 기존에 객체나 빈 문구가 들어왔을 때의 표시를 안전한 대체 문구로 바꾼 점은 의도한 개선이다.
- `apiFetch`의 성공 `data` 반환, 실패 코드에 따른 쿠키 지우기, 대시보드의 성공 응답 전체 반환, 조회 훅의 상태·로케일 대체 문구를 바꾸지 않았다. 문의·라우팅·백엔드·정책·의존성·lockfile은 변경하지 않았다.

파싱 실패 시 기존 `res.json().catch(() => null)`을 유지한다. [Response.json](https://developer.mozilla.org/en-US/docs/Web/API/Response/json)은 JSON의 원시 값도 반환하며 잘못된 JSON에서는 실패할 수 있어 파싱 결과를 객체로 가정하지 않는다. [Response.ok](https://developer.mozilla.org/en-US/docs/Web/API/Response/ok)의 기존 HTTP 성공 판정도 유지한다.

## 검사와 재현

기준 main은 `c8c5489a662ae9aab354335483332116f1962072`다. 독립 D: worktree에서 기존 의존성을 재사용했으며 설치·서버·실제 API 요청은 하지 않았다.

- 프런트 순수 유닛 **91개 통과**. 새 오류 문구 검사 25개와 기존 66개를 포함한다. TypeScript 테스트 컴파일 뒤 Node 검사를 직렬 실행했다.
- 실제 `apiFetch`와 대시보드 `request` 소스를 사용한 fetch 대체 검사 **20조건 통과**. 공통 400·403·404·413·500, 기존 오류, HTML·빈 응답, 성공 반환, 인증 만료의 코드와 쿠키 지우기를 확인했다.
- 같은 도구로 기준 커밋의 두 호출부를 읽었을 때는 공통 문구 10조건 모두 HTTP 대체 문구로 바뀌는 것을 확인했다. 성공 API가 실패한다는 재현이 아니라 오류 문구 선택의 재현이다.
- 변경 TS 5파일의 ESLint와 변경 생산 코드 4파일의 타입 검사가 통과했다. 전체 프런트 타입 검사는 512MB 힙 한도에서 중단됐으므로 통과로 기록하지 않는다. Next production build는 실행하지 않았다.

재현 도구: `node tools/frontend-review/check-api-error-callers.cjs --output <검사결과.json>`. 루트에서 실행하며 기존 프런트 TypeScript와 기준 Git 커밋이 필요하다. 별칭·API 주소·사용하지 않는 React import만 대체하고 실제 응답 처리 코드를 읽는다. fetch와 DOM은 합성 fixture이며 실제 브라우저·쿠키 저장·React 렌더 검사가 아니다. 공개 조회 훅 자체는 마운트하지 않았다. 추가 결과·소스 해시는 [검사 기록](evidence/frontend-errors-20261028/validation.json)에 있다.

## 검토와 한계

다른 회사 모델의 최신 diff 검토가 끝나기 전까지 Draft로 유지한다. 이후 검토 결과는 PR 본문과 댓글에 기록하고 이 문서의 검사 당시 상태와 구분한다. 같은 회사의 보조 조사는 다른 회사 또는 사람의 승인으로 쓰지 않는다.

프런트는 서버가 공개 문자열로 보낸 기존 오류를 표시한다. 서버의 모든 메시지가 공개에 적합한지 전수 검사한 것은 아니다. PR #42의 고정 400·413과 공개 오류 정리는 별도 미병합 변경이며 이 프런트 수정은 기존 오류 계약도 계속 읽는다. 실제 배포·화면·전체 타입·build·운영 데이터·로그는 미검증이다. 병합·배포는 하지 않았다.

기존 checkout의 변경과 열린 다른 브랜치는 사용 중이어서 정리하지 않았다. 새 도구는 이 문제의 재현을 위해 추가했으며 패키지·의존성 설정은 바꾸지 않았다.
