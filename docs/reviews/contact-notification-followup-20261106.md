# 문의 알림 지연과 접수 응답 분리

기준 `8ba4e84`. 병렬 코드 검토에서 지속 저장 뒤 `notifyReceipt`를 무제한 기다리는 경로를 찾았다. 프런트는 15초에 요청을 취소하므로, 알림 DB 지연만으로 저장된 접수가 실패처럼 보일 수 있었다.

라우터는 이제 저장 결과를 먼저 응답한 뒤 알림을 별도 Promise로 실행한다. 동기 예외와 늦은 거부 모두 처리한다. 재전송 시 같은 접수번호·알림 중복 키를 유지한다. 알림은 기존처럼 최선 노력이며 프로세스 종료까지 견디는 큐나 자동 재시도 작업을 추가한 것은 아니다.

## 확인

- 검토자가 실제 라우터의 최종 handler를 메모리 저장 stub·미완료 알림 Promise와 실행: 알림이 끝나기 전 응답 없음, 완료 직후 201을 확인. 서버·운영 DB를 사용하지 않은 원인 재현.
- 기존 MongoDB 7.0.24 바이너리와 새 임시 DB로 문의 검사 **20/20 통과**. 기존 18개에 지연 알림·동기 예외 두 경우 추가.
- 미완료 알림 상태에서 신규 201과 재시도 200 각각 1초 응답 제한을 통과, 같은 접수번호와 DB 한 문서 확인. 응답 후 알림을 reject해도 처리되고 문서 유지.
- 실제 알림 중복 방지 검사는 알림 Promise 완료 후 문서 수를 검사하도록 조정. 고객 개인정보 복사 없음과 알림 한 건 유지 확인.
- 수정한 두 파일 ESLint와 node 구문 검사 통과. 검사 후 Prettier가 두 파일의 서식만 정리했고 다시 ESLint 통과. 앱 빌드·프런트 테스트는 변경 범위가 없어 반복하지 않음.
- 로컬 4192의 이전 서버 프로세스·리스너가 없어 이 세션 소유의 잔여 잠금을 정리했다. DB 검사 뒤 기존 프런트 빌드를 숨김 서버로 복구해 `/en/landing` 200 확인. 다른 앱·세션 프로세스를 종료하지 않음.

검토·테스트 에이전트는 OpenAI 계열이다. 타사 교차 리뷰를 대체하지 않으며 Draft를 유지한다. 실제 운영 알림 수신·승인 정책·문의 제출·배포는 미검증이고 운영 DB·환경값은 변경하지 않았다.

검사 로그와 해시는 [증빙](evidence/contact-notification-20261106/validation.json)에 있다. 이번 변경은 backend 응답 순서이며 화면을 변경하지 않았다. 회사소개·문의 실제 프리뷰 캡처는 [기존 화면 증빙](evidence/preview59-20261106/README.md)에 보존한다.
