# 이슈 중심 작업 절차

사용자가 승인한 COSMOS-TVC-Hopper의 AGENTS.md 작업 순서와 이슈·PR 양식에서 이슈 선점, 독립 작업, 다른 회사 모델의 리뷰, 후속 이슈 연결 절차를 가져왔다. JSL의 승인 디자인과 기존 PR·병합 절차를 유지한다.

## 시작과 소유권

1. 관련 이슈와 모든 댓글을 읽는다. 닫힌 이슈나 다른 작업자의 선점이 있으면 중복 작업하지 않는다.
2. 상위 목표는 PRD 이슈로 정리하고 실제 구현은 검증 가능한 작은 작업 이슈로 나눈다. 상위 목표가 없으면 독립 이슈로 진행한다.
3. 이슈에 목적, 확인한 배경, 할 일, 판정 기준, 제외·보존 범위, 담당자와 사람이 해야 할 일을 쓴다. GitHub assignee를 실제 지정한다. 같은 계정을 함께 쓸 때 assignee는 계정 소유자를 나타내므로 제작·검토 모델과 작업 세션 식별자는 이슈 본문과 선점 댓글에 별도로 적는다. 비밀값·연락처·대화 원문은 적지 않는다. PRD에는 목표, 범위, 하위 작업과 완료 기준을 적는다.
4. 열린 PR·브랜치·worktree를 확인한다. 같은 작업은 기존 브랜치를 재사용한다. 새 작업은 최신 기본 브랜치에서 작업 브랜치와 독립 worktree를 만든다. Codex의 기본 접두사는 `codex/`이며 다른 도구는 프로젝트와 사용자 지시를 따른다. 기존 브랜치는 이름 때문에 재구성하지 않는다.
5. 브랜치가 실제로 생긴 뒤 이슈에 `claimed by <branch>`를 남긴다. 담당을 바꾸거나 중단하면 댓글로 해제·인계를 기록한다.
6. 제작 에이전트 1명과 제작에 참여하지 않은 다른 회사 모델의 검토 에이전트 1명으로 진행한다. 공유 파일 작성자는 한 명이다. 병렬 작업은 별도 이슈로 나누고 이슈마다 제작 1명과 다른 회사의 검토 모델 1명을 정한다. 이슈 간 공유 파일의 작성자는 한 명으로 지정한다.

브랜치는 가능한 한 main 포함 4개 이하로 유지한다. 개수를 맞추려고 사용 중이거나 미병합·미푸시 작업 또는 다른 작업자의 브랜치를 삭제하지 않는다. 정리를 미루면 이유를 보고한다.

## 구현과 검증

- 관련 공식 문서와 기존 구현을 확인하고 출처를 PR에 적는다. 이슈 범위만 변경한다.
- 현재 사용자 승인과 이슈의 변경·보존 범위를 따른다. 과거 제안이나 초안의 상태를 새 승인으로 해석하지 않는다.
- 변경 영역에 맞는 테스트·타입·lint·빌드를 실행한다. 문서만 바꾸면 구조·링크·diff 검사를 하고 앱 검사를 생략한 이유를 쓴다.
- 화면 변경은 같은 화면 크기·카메라의 전후 캡처로 비교한다. 관련 데스크톱·모바일 크기와 진행률, 역방향·동작 줄이기 검증 여부를 기록한다.
- 관찰, 추론, 미확인을 구분한다. 미실행 검사나 저해상도 표본을 최종 품질 통과로 쓰지 않는다.

## PR과 교차 리뷰

1. 실제 변경을 의미 있는 단위로 커밋하고 일반 푸시한 뒤 Draft PR을 만든다. 같은 작업의 PR이 있으면 갱신한다.
2. 이슈를 끝내는 PR은 `Closes #번호`, 일부 작업이나 참고 관계는 `Refs #번호`로 연결한다.
3. 제작 모델과 다른 회사의 검토 모델 1명이 최신 diff를 리뷰한다. 요청에는 범위를 주고 원하는 결론을 유도하지 않는다. 관련 이슈와 문맥은 검토자가 읽을 수 있어야 한다.
4. 유효한 지적은 수정한다. 반영하지 않은 지적은 이유를 남긴다. 모델 이름, 검토한 head SHA, 검사 범위와 한계를 기록한다.
5. 같은 GitHub 계정의 AI 검토를 독립된 사람의 GitHub 승인으로 표현하지 않는다. 모델 연결이 막히면 리뷰 미완료로 기록한다.
6. 교차 리뷰 미완료인 PR은 Draft를 유지한다. 예외는 사용자가 명시적으로 승인한 경우에만 이유를 기록한다. AI 교차 리뷰는 사람 승인이나 저장소의 필수 리뷰 요건을 대신하지 않는다. 검증 후 일반 PR로 전환한다. 병합 직전에 최신 head/base SHA, CI, 리뷰와 변경 요청을 다시 확인한다. 미해결 변경 요청이나 운영 문제를 남긴 채 병합하지 않는다.
7. 최종 diff 전체에서 비밀값·개인정보와 승인 범위를 점검한다.
8. 병합·배포는 별도 절차와 사용자 승인 범위를 따른다. 병합과 운영 배포는 사용자가 명시적으로 지시한 범위에서만 수행한다. 이 절차 도입 자체를 병합·배포 승인으로 해석하지 않는다.

## 후속 작업과 완료

- 범위 밖 결함, 남은 작업, 미검증 항목, 미룬 결정은 중복 확인 후 각각 후속 이슈로 만든다. 같은 판정 기준의 세부 메모는 기존 이슈 댓글에 묶는다.
- 후속 이슈에는 근거, 다음 행동, 판정 기준, 담당자와 선행 조건을 적고 원래 PR에 번호를 연결한다. 조회만 했다는 이유로 빈 이슈를 만들지 않는다.
- 외부 입력이 필요하면 필요한 사용자 행동과 막힌 이유를 기록한다. 로그인·권한 동의·결제 등의 사용자 절차를 대신 승인하지 않는다.
- 완료 보고에 변경, 검사, 한계, 후속 이슈, 프로젝트 커밋·푸시·PR 상태를 적는다.
- 각 에이전트에 별도로 적용되는 개인 작업 기록 규칙을 유지한다. Codex의 독립 기록은 프로젝트 Git 처리와 구분한다. 기록 성공을 프로젝트 검증·병합·배포 성공으로 표현하지 않는다.

병합 후에는 이슈 닫힘과 선점 종료를 확인한다. 본인 브랜치를 정리하기 전 커밋의 기본 브랜치 보존, 열린 PR, 미푸시 변경, 다른 세션의 worktree 사용을 확인한다. 사용 중이면 삭제하지 않고 정리를 미룬 이유를 보고한다.

문서 검사는 `git diff --check`, 변경 파일 목록과 로컬 Markdown 링크 대상 확인, 이슈 YAML 파싱으로 수행한다. 도구가 없거나 실행하지 못한 검사는 그대로 보고한다.

## 기존 작업의 전환

열린 PR과 사용 중인 작업 폴더를 보존한다. 기존 PR을 재구성하거나 닫지 않는다. PR 본문과 리뷰에서 실제 남은 항목을 수집하고 중복을 제거해 후속 이슈로 연결한다. 이슈가 없다는 이유로 이미 완료한 작업을 다시 구현하지 않는다. 먼저 작은 작업 하나로 절차를 시험한다.

COSMOS 전용 학생 담당자, 고정 리뷰어, 수업용 이해 확인, 하드웨어 검사는 복제하지 않는다. 스크립트 전체 이식과 자동화 추가는 별도 이슈로 다룬다.
